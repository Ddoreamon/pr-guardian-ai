# V4.5 shadow-mode design (proposal) — not wired into production

The gate is accurate on the sets measured this round, but the robustness work also
showed how easily a dependency class can be missed. That is exactly the profile for
**shadow mode**: compute, display, never act.

## 1. What shadow mode does

After a review finishes, compute a sufficiency verdict from the artefacts the review
already produced. It never runs before or during the review, and it never influences
it.

```
review completes
   → report.evidence_sources (file, span, kind, call id, truncated)
   → rebuild registry by re-reading the pinned snapshot
   → derive obligations from (base, head, diff) at that snapshot
   → assess
   → attach as a separate artefact: review.evidence_sufficiency
```

Because `evidence_sources` is already in the report, the verdict can be recomputed
offline at any time from `(repository, base_sha, head_sha)`. No model call, no extra
network, no new repo access.

## 2. Non-interference guarantees

| Requirement | How |
|---|---|
| never blocks a PR review | computed after the review returns; failures are swallowed and recorded as `unknown` |
| never changes `suspected` / `confirmed` | the gate only reads the registry; findings are not touched |
| never changes `review_status` | `review_status` is derived from execution records; the gate is a separate field |
| no new untrusted-code execution | it re-reads the same allowlisted files; no tests, no shells |
| no effect on the model budget | no model call; no tools are exposed |
| recomputable per SHA | inputs are the pinned snapshot plus a serialised registry |
| shows missing/unknown obligations | `missing_obligations` and `unknown_obligations` ids, with file/span/rationale per obligation |
| not confused with source verification | separate field name and separate UI label: `sufficiency: insufficient` never renders as `source_verified` or `confirmed` |

## 3. Proposed report shape (additive, defaulted)

```json
"evidence_sufficiency": {
  "status": "insufficient",
  "assessment_version": "v4.5.2",
  "snapshot_sha": "…",
  "obligations": [{"obligation_id": "ob-…", "kind": "caller_usage",
                   "file_path": "src/report.py", "required_span": [6, 8],
                   "status": "missing", "rationale": "…"}],
  "missing_obligations": ["ob-…"],
  "unknown_obligations": [],
  "explanation": "required evidence was not delivered for: ob-…"
}
```

All fields default, so historical reports keep parsing. The field is `null` when
shadow mode is off.

## 4. UI wording (draft)

> **Evidence sufficiency: insufficient.** This review did not read 1 of the
> evidence ranges its own change implies (`src/report.py:6-8`, because `render`
> changed its signature). This is a coverage check, not a defect verdict: it does
> not mean the code is wrong, and `sufficient` would not mean the code is right.

## 5. Rollout

1. flag `PR_GUARDIAN_SUFFICIENCY_SHADOW=1`, **default off**;
2. compute only for reviews that used tools (a V1 diff-only review has no registry);
3. store the verdict in the report and log it; nothing else reads it;
4. after ≥ 30 real reviews, compare verdicts against human review: count
   insufficient verdicts that a reviewer confirms were real evidence gaps
   (precision) and gaps the reviewers saw but the gate missed (recall).

## 6. Decision

**Conditional Go for shadow mode, No-Go for enforcement.**

* Enforcement is not justified: the robustness round found three false sufficients in
  the *pre-fix* deriver, and the fixed version is validated on 10 authored cases, not
  on real reviews. A gate that can be wrong in the "sufficient" direction must not
  block anything.
* Shadow mode is justified because it cannot block, cannot change findings and
  cannot spend budget, while it produces exactly the data needed to bound the
  false-sufficient rate on real traffic.
* Prerequisite before enabling even in shadow mode on a shared deployment: the
  ≥ 30-review agreement study above, plus a rule that a shadow verdict is never
  displayed next to a `confirmed` finding without saying the two are unrelated.

## 7. Open risks for shadow mode

* `evidence_sources` does not carry `complete_lines`; rebuilding the registry re-reads
  the snapshot and recomputes them, which must use the same V4.1 truncation rules.
* A review whose repository has moved since the review (force-push) cannot be
  recomputed; the verdict must then be `unknown`, not stale.
* Dynamic dispatch and data-flow aliasing remain blind spots; they surface as
  `unknown` only when a decorator or a module-level mapping is visible.
* Cost: ~0.3–0.4 s per review for derivation, plus a read of the touched files.
