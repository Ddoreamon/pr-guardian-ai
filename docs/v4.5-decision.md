# V4.5 decision — Evidence Sufficiency Gate

Offline assessment only. Nothing is wired into the review pipeline, no `suspected`
finding changes, no new repo access, no extra API key. Default state: the module is
imported by tests and the offline evaluator, nothing else.

## 1. What was built

| Piece | File | Purpose |
|---|---|---|
| `EvidenceObligation` | `src/pr_guardian/sufficiency.py` | one evidence duty, derived from the diff |
| `derive_obligations(head, base, changed_files)` | same | diff → enclosing definitions → callees → callers (on contract change) → config constants → dynamic flags |
| `EvidenceSufficiencyResult` | same | `sufficient` / `insufficient` / `unknown`, plus fulfilled / missing / unknown ids and the evidence refs used |
| `assess(registry, obligations, sha, allowed)` | same | re-runs V4.1 `validate_ref` for every obligation |
| Held-out set + profiles | `scripts/sufficiency_cases.py` | 7 cases, scripted deliveries, negative controls |
| Evaluator | `scripts/sufficiency_eval.py` | dev traces + held-out profiles, metrics |

Obligations are derived **only** from the pinned snapshot, the diff, ASTs and the
index; `derive_obligations(head, base, changed_files)` accepts nothing else, and a
test pins that signature.

## 2. Results (`docs/v4.5-eval/`)

| metric | value |
|---|---|
| scored profiles | 33 (7 held-out cases × 2–3 delivery profiles + 3 negative controls each) |
| status accuracy | **100%** |
| false sufficient | **0** |
| false insufficient | **0** |
| unknown rate | 2.2% (the dynamic-dispatch case) |
| obligation kind precision / recall | 1.00 / 1.00 |
| mean assessment cost | 63 ms |
| mean derivation cost (per diff) | 295 ms |

Dev data (real V4.4 traces, both arms): **12 / 12 `sufficient`**. Every recorded run
had already delivered the obligations the gate derives — including `B1`, where the
`money.py` *read* was denied but `find_symbol_definition("to_cents")` had already
delivered that definition.

## 3. The false sufficient that was found, and fixed

The first version derived caller obligations **only across files**. A required
parameter added to `price()` whose only caller sits in the same file therefore
produced no caller obligation at all.

Control `H7-same-file` delivered only the changed function (span 4–6): the gate
returned **`sufficient`**, which is a false sufficient — the caller was never read
and would break at runtime. This was the highest-risk error class the task asks
about, and it was real.

Fix: when the contract changes, callers in the same file are included too (only the
modified chunk itself is skipped). Re-run: 0 false sufficient, recall 1.00. A
regression test (`test_same_file_caller_is_required`) pins it.

Disclosure: `H7` was added *after* the gate existed, as an adversarial control, and
the fix was made in response to it. It is therefore a **debug case**, not an
independent held-out case. The remaining six cases were written before the gate ran,
but by the same author who designed the derivation, so they share its assumptions.

## 4. Answers to the five questions

1. **Does sufficiency find real gaps that source verification misses?**
   On the available real traces, **not yet**. Source verification already reports
   which lines arrived; the gate adds the obligation layer, but in 12 real
   assessments every obligation was already covered. Its one genuine catch was a
   *structural* blind spot (same-file callers), found with a constructed control, not
   with recorded model behaviour.
2. **Did it wrongly reject reviews that had enough evidence?**
   No false insufficients were observed: 33/33 profiles matched, and all 12 real
   traces were `sufficient`. Local-only changes (`H5`, `H6`) are not forced to read
   other files, which was the main over-strictness risk.
3. **Is there a false sufficient, and how serious?**
   One existed (same-file caller), severity high — it would have declared a breaking
   change sufficiently reviewed. It is fixed and regression-tested. After the fix,
   none in this evaluation; with n = 33 curated profiles that is a weak guarantee,
   not a proof.
4. **Does it depend on hidden gold or case-specific rules?**
   No gold, no hidden tests, no case identifiers: derivation is diff + AST + index
   only. The V4.4 required-range logic *did* seed spans from gold locations, and this
   audit records that as a defect that V4.5 replaces. The one case-specific artefact
   is `H7` itself, added as a control after the fact.
5. **Should it be wired into the production pipeline?**
   **No, not as an enforcement gate.** Recommendation: a **shadow-mode** experiment
   only — compute the verdict, report it, never block or re-label anything — until
   the gate is measured on a genuinely independent case set (≥ 20 cases, written by
   someone other than the derivation's author) and the false-sufficient rate can be
   bounded. The evidence at hand is exploratory: 7 cases, 33 curated profiles, a
   metric that is at its ceiling, and one control that had to be fixed during the
   evaluation.

## 5. Why not claim success

* Every scored profile was constructed by the same author as the derivation, so the
  100% agreement measures internal consistency more than predictive validity.
* The profiles are cleanly separable (whole file vs callee-only); real traces are
  messier and all came out `sufficient`, i.e. the discriminating regime is untested.
* The dev set has no insufficient case at all, so "detects real gaps" rests on
  synthetic controls.
* Obligation kinds are coarse: the model does not distinguish a changed default from
  a changed exception type at the same confidence, and `boundary_condition` is
  declared but never derived.

## 6. Limits and risks

* `unknown` currently fires only on dynamic calls/unpacking; polymorphic dispatch
  through registries, decorators or `__getattr__` is not detected unless the call
  site itself looks dynamic.
* Caller discovery is one hop and name-based: aliased imports, `functools.partial`,
  or a method called through an attribute chain can be missed.
* A callee whose contract changes but which is only called dynamically yields
  `unknown`, not `insufficient` — conservative, but it can hide a duty.
* Assessment is cheap (63 ms) but derivation costs ~0.3 s per diff, which is real
  money on large repositories.
* The gate never judges claims: a `sufficient` verdict with a wrong finding stays
  `claim_unjudged`, exactly as in V4.1.
