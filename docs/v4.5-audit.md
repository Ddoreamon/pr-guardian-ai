# V4.5 audit — what the existing evidence mechanism actually proves

Read before building the gate. Sources: `evidence.py`, `models.py`, `pipeline.py`,
`tool_calling.py`, `repo_index.py`, `scripts/budget_eval*.py`,
`docs/v4.4-comparison.md`.

## 1. The registry is sound, the coverage metric around it was not

`EvidenceRegistry` records only what was delivered, after truncation:

| Field | Meaning |
|---|---|
| `tool_call_id`, `tool_name` | which provider call delivered it |
| `ref` | the commit SHA carried by the tool payload, checked against the registry |
| `file_path`, `start_line`, `end_line` | the delivered window |
| `complete_lines` | every numbered line whose *whole text* arrived |
| `kind` | `read` / `symbol` are citable; `candidate` (a search hit) never is |
| `truncated` | the final physical line is dropped when set |

`validate_ref` then requires the cited range to lie inside `complete_lines`, the
path to be in the allowlist, the SHA to match, and the delivering call to exist.
That part is trustworthy.

The V4.4 scorer (`scripts/budget_eval.py::_covered`) only asked whether *some*
registry entry's `[start, end]` contained the required range. It did not re-check
the SHA, the call id, or the kind; it trusted `entry.kind` to be `read`/`symbol`
but did not re-validate the ref. V4.5 closes that by calling `validate_ref` for
every obligation.

## 2. Four specific defects found in the V4.4 coverage logic

1. **Gold-seeded required ranges.** `freeze()` derived `required_evidence` from the
   case's gold `(file, qualname, line)`. The *ranges* were computed from the index,
   but *which* function to demand was chosen from the answer. That is exactly the
   "derive obligations from gold" pattern the V4.5 rules forbid.
2. **Caller demanded unconditionally.** The caller span was added whenever a
   cross-file call edge existed, regardless of whether the contract changed. A pure
   refactor (`C3-refactor`) therefore demanded the caller even though the signature,
   raised exceptions and return shape were unchanged — over-strict, and it is what
   penalised the V4.4 planner.
3. **Same-file callers invisible.** The derivation only walked cross-file edges, so
   a signature change whose only caller sat in the same file produced *no* caller
   obligation at all. V4.5 reproduced this as a real **false sufficient** on the
   `H7-same-file` control, then fixed it (`other.file_path == chunk.file_path` is
   now allowed; only the modified chunk itself is skipped).
4. **File-level correctness proxy.** `_judge()` counts a bug as detected when a
   finding is anchored on the changed *or* gold file. That is a detection proxy, not
   a correctness test; it is fine for the A/B, but it says nothing about whether the
   claim is right.

## 3. C3-refactor, precisely

V4.4 planner read `src/stock.py` only and skipped `src/checkout.py`. Under the V4.4
required-evidence rule that was a lost range (2/2 → 1/2). Under a contract-based
rule there is no caller duty: `reserve` keeps its arguments, its raised exception
and its `return` shape (`BinOp` before and after), so a caller cannot break.

Both statements are true; they measure different things. V4.5 replaces "read the
caller because it exists" with "read the caller because the contract changed", and
records C3 as a case where the earlier metric was stricter than the semantics
warrant.

## 4. What the gate must add

The existing stack can say *"these lines were delivered"* (source verification) and
*"the process finished"* (completeness). It could not say *"the evidence the diff
obliges a reviewer to obtain is present"*. That is the only new question V4.5
answers, and it must be answered without gold labels, hidden tests or model
self-reports.
