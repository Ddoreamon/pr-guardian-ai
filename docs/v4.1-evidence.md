# V4.1 — Evidence provenance for AI findings

Branch `feature/v4-agent-reliability`, stacked on `feature/v3-repo-rag` (Draft PR
#5). `main`, Render and both frozen held-out sets are untouched.

Acceptance question: *for every AI finding, can we prove the cited source really
came from the GitSnapshot this review read — and keep "the source is real" separate
from "the claim is right"?* After this change: **yes to the first; the second stays
explicitly unjudged.**

---

## 1. Audit of the chain before this change

| Stage | What existed | Real or free text |
|---|---|---|
| DeepSeek finding | `file_path`, lines, summary, explanation, `evidence` | **free text**; `evidence` was never checked |
| Tool trace | per call: name, args, outcome, `call_id`, `result_chars` | real, but not linked to findings |
| GitSnapshot | pinned SHA, allowlist, read-only | real |
| Validator | anchoring, dedupe, no self-confirmation | real, but only checks *location*, not provenance |
| ReviewReport | `llm_findings`, `final_findings` | no provenance fields at all |

So a finding's `evidence` string could describe code the model never saw, and
nothing in the report would contradict it. That gap is what V4.1 closes.

## 2. Model metadata on partial runs

`pipeline` reported `model_name = "none"` unless the status was `ok` or `failed`,
so a `partial` review — which really did call DeepSeek and really spent tokens —
was attributed to no model.

Fixed with `_reported_model()`: the model is named when **any** request was actually
made (`tool_model_calls > 0`, tokens > 0, or status in `ok/failed/partial`);
otherwise `"none"`. Tokens, request counts and tool status come from the same run,
and a `partial` report keeps its `PARTIAL` note, so it cannot read as a finished
clean review. Regression tests cover partial, unconfigured and policy-disabled runs.

## 3. EvidenceRef and the registry

`EvidenceRef` (on each finding): `ref`, `file_path`, `start_line`, `end_line`,
`tool_call_id`, `tool_name`, `evidence_status`, optional `snippet_sha256`.

`EvidenceRegistry` records **what the model actually received**, after truncation:
one entry per delivered range, with the provider `tool_call_id`, the pinned SHA,
the tool name, hit/truncated flags and a snippet fingerprint.

| Tool | Recorded ranges |
|---|---|
| `read_code_context` | the delivered `file_path` + `start_line`..`end_line` |
| `find_symbol_definition` | line numbers parsed from the delivered snippet (i.e. what the model saw) |
| `search_code` | each delivered hit's `start_line`..`end_line` |

`miss`, `error` and `budget_denied` are **not** recorded: a refused call cannot back
a citation. Truncation is honoured — only surviving ranges are citable.

## 4. Verification rules (deterministic)

`evidence.validate_ref()` returns `source_verified` or `source_unverified` plus a
reason, in this order:

| Check | Failure reason |
|---|---|
| a real 40-hex `ref` that differs from the snapshot | `sha_mismatch` |
| `file_path` in the snapshot allowlist (`src/**/*.py` via `TrustedCodebase`) | `path_not_allowed` |
| `1 <= start_line <= end_line` | `bad_range` |
| registry built for the same SHA | `registry_sha_mismatch` |
| some delivered entry covers the cited range | `not_delivered_to_model` |
| that entry has a provider call id | `evidence_has_no_call_id` |

A non-SHA `ref` (a label, an empty string) is a **formatting slip**: the commit is
pinned by the review and the model cannot choose one, so the citation is verified
against the snapshot and the real SHA is written back.

**Call attribution is resolved by the registry, not by the model.** Provider
`tool_call_id`s are opaque strings a model cannot reliably echo; the earlier smoke
run proved it (it put the commit SHA and file labels there). Verification is
therefore by file + line range, and the registry attributes the citation to the call
that actually delivered it. If the model echoes a different id, the finding keeps
its verified source and records `model_tool_call_id_unrecognised`.

One bad citation taints the finding: provenance is `source_unverified` unless every
cited range resolves.

## 5. Source verification is not correctness

| Field | Meaning |
|---|---|
| `evidence_status` | `source_verified`, `source_unverified`, `no_evidence_ref`, `deterministic`, `not_evaluated` |
| `claim_status` | `claim_unjudged` for every LLM finding; `deterministic` for ruff/pytest |
| `verification_status` | unchanged: `suspected` for LLM findings, `confirmed` only from deterministic tools |

No code path can set `semantically_confirmed`; nothing upgrades `suspected` because
a source verified. A finding with a real citation and a wrong explanation stays
`source_verified` + `claim_unjudged` + `suspected` — exactly what the clean-case
smoke shows below.

## 6. Transparency and compatibility

* Original LLM findings are **kept**; provenance is added beside them.
* `final_findings` still holds everything the validator accepts; unverified ones are
  flagged, never silently dropped.
* `trusted_findings` is the high-confidence view: source-verified or deterministic.
* New report fields are all defaulted, so a pre-V4.1 report still parses (tested),
  and frozen benchmark JSON is unaffected.

## 7. Real DeepSeek evidence chain (`docs/v4-evidence-smoke/`)

Two development cases, MCP backend, real provider, `model_name` now recorded as
`deepseek-flash`, both `partial` (5 model calls each):

| Case | Findings | Citations | Source verified | Claim | Verdict |
|---|---|---|---|---|---|
| bug (cents vs units) | 1 | 3 | **1** | `claim_unjudged` | `suspected` |
| clean (`note="web"`) | 1 | 2 | **1** | `claim_unjudged` | `suspected` |

The bug finding is correct and its three citations resolve to real delivered
ranges (`checkout.py:6-9` from `read_code_context`, `invoices.py:23-26` from
`find_symbol_definition`, `orders.py:6-8` from `search_code`).

The clean-case finding is a **low-severity false positive** ("apply_credit accepts
`note` but never uses it"). Its sources are genuinely verified — the model did read
those lines — and the claim is still marked unjudged and the verdict stays
`suspected`. That is the distinction this milestone exists to make visible.

### What the first attempts showed

The first real run produced **0 verified findings**. Two contract bugs, both fixed
in the code rather than papered over:

1. the model was asked to echo `tool_call_id`, which it cannot see; it echoed the
   SHA instead → attribution now comes from the registry;
2. the pinned SHA was never shown in the prompt, so `ref` held labels like
   "checkout" → the SHA is now in the user prompt, and non-SHA values are
   normalised instead of being read as a different commit.

Neither change weakens verification: a real 40-hex SHA pointing at another commit is
still rejected, and a range that was not delivered still fails.

## 8. Remaining risks

* Verification proves delivery, not comprehension: a model can cite real code and
  still misread it (see the clean case).
* Ranges are syntactic: if a tool returned lines 10–20, citing 12–13 verifies even
  if the semantic basis is elsewhere in those lines.
* `find_symbol_definition` ranges come from the rendered snippet; a very long
  symbol is truncated, and only the visible lines are citable.
* The registry lives in memory for one review; it is not persisted or signed.
* The model may cite a delivered range that is irrelevant to its claim — provenance
  says "you saw this", never "this proves your point".
* Both smoke runs were `partial` on the call budget; they are engineering checks,
  not accuracy measurements.
