# V4.2 — Review completeness

Branch `feature/v4-agent-reliability` (Draft PR #5). Process state only: this
milestone says whether a review *finished*, never whether the code is correct.

## 1. Why

Repeated real runs ended in `tool_limit` + `partial`, and the report had no
first-class way to say so: `llm_status` mixed "the model ran" with "the
investigation finished", and a partial run that reported nothing was
indistinguishable from a clean one.

## 2. States

| `review_status` | Meaning |
|---|---|
| `completed` | the flow reached its configured end |
| `partial` | tool budget or rounds ran out; coverage is incomplete |
| `failed` | a model request, protocol or parse error made completion impossible |
| `not_run` | no model was enabled (no key, policy, or user request) |

Derived from execution records (`tool_calls`, `model_requests`, `model_failures`),
never from anything the model says about itself.

## 3. `ReviewCompleteness`

| Field | Content |
|---|---|
| `status`, `reason` | the state above and why (`tool_budget_exhausted`, `no_api_key`, …) |
| `tool_rounds_used` / `tool_rounds_max` | rounds consumed vs configured |
| `tool_calls_used` / `tool_calls_max` | calls attempted vs configured |
| `tool_calls_denied`, `denied_requests` | how many were refused, and which tool+arguments |
| `model_requests`, `model_failures` | provider traffic, separately from tools |
| `tool_errors`, `tool_misses` | tool-side failures, separately from provider failures |
| `duplicate_calls` | identical `(tool, arguments)` issued more than once |
| `findings_signal` | `has_findings`, `no_findings_in_completed_review`, `not_evaluated` |

`findings_signal` is the guard against the misleading case:

* `partial` + 0 findings → **`not_evaluated`** (never "clean");
* `completed` + 0 findings → `no_findings_in_completed_review`, and the UI says
  this means nothing was flagged in this pass, not that the change is defect-free.

## 4. Findings are grouped by provenance, not by confidence

`deterministic_findings`, `source_verified_findings`, `source_unverified_findings`
are separate lists on the report. A source-verified LLM finding stays
`claim_unjudged` + `suspected`; only ruff/pytest produce `confirmed`. The UI banner
for a verified finding says its code was seen, never that the defect is confirmed.

## 5. UI

One banner above the result grid (`#completeness-banner`) renders the state:

* `partial`: "PARTIAL review: the tool budget ran out … 4/4 tool calls used, 2
  refused. no findings — NOT a clean review, coverage is incomplete.";
* `failed` / `not_run`: the reason;
* `completed` with zero findings: the explicit "does not prove the change is free of
  defects" wording;
* `completed` with findings: no banner.

## 6. Compatibility

`review_status`, `completeness` and the three finding groups all have defaults, so
pre-V4.2 reports parse unchanged (`completeness.status == "completed"`), and the
frozen benchmark JSON is untouched.

## 7. Tests

`tests/test_review_status.py` (14, no model calls): completed with/without findings,
partial with/without findings, duplicate reads, tool errors vs model failures, the
three `not_run` paths, model error → `failed`, verified-vs-confirmed grouping, and
legacy report parsing.

## 8. Limits

* `completed` still depends on the model returning schema-valid JSON; a valid but
  shallow review is `completed`.
* Duplicate detection compares exact argument dictionaries, so semantically equal
  but differently formatted arguments are not merged.
* The budget is unchanged (`4` calls). This milestone makes exhaustion visible; it
  does not hide it behind a larger budget.
