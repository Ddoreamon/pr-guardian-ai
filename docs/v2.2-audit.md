# V2.2 audit — review target, label rules and scorer fixes

Date: 2026-10-27. Branch `feature/v2-function-calling`. No held-out run had been
performed when this audit was written, so the revisions below are pre-registered,
not fitted to any output.

---

## 1. The question that had to be settled first

The V2.1 Dev run exposed a label problem in P2-b, P3-b and P5-b (and would have
exposed it in P9-b, P11-b): the **outer service** behaved identically, but the
**changed function's own documented contract** no longer held. Those variants had
been labelled "clean" because their tests passed.

Two candidate rules were available:

| Rule | What counts as a defect | Consequence |
|---|---|---|
| S · service observability | only a regression visible at the service entry point | contract violations in the changed function become "clean" |
| F · documented contract | a violation of annotations, docstrings, or the behaviour the surrounding code establishes | passing tests are necessary but not sufficient |

**Rule S was rejected.** It would call `search()` returning `None` behind a
`-> list[dict]` annotation "clean", which is exactly the "tests pass, therefore it
is fine" fallacy the audit was asked to remove. A code-review agent that ignores
a broken annotation is not reviewing.

**Rule F was adopted**, and it is now stated identically in both model prompts
(`REVIEW_SCOPE` in `llm_reviewer.py`, reused verbatim by `tool_calling.py`):

> judge the change against the contracts documented in this repository — type
> annotations, docstrings, and the behaviour established by the surrounding code,
> including other files. A passing test suite is NOT proof that a change is
> correct.

### The consequence that forced redesigns

The changed file is **byte-identical in both variants**. Any contract written
inside that file therefore applies equally to A and B. If the diff broke it, B
could not be clean under Rule F. So a valid pair requires the diff to violate
only the **external** context.

Auditing the 11 pairs against that test:

| Pair | Contract violated by the diff | Written where | Verdict |
|---|---|---|---|
| P1 | `apply_rate` signature | context (rates.py) | valid |
| P2 (v1) | `tax_for` says "expressed in dollars" | **changed file** | invalid → redesigned |
| P3 (v1) | `-> list[dict]` vs `return None` | **changed file** | invalid → redesigned |
| P4 | none in the changed file | context | valid |
| P5 | none documented (no `raises` clause) | — | valid |
| P6 | none (docstring keeps `None` semantics) | — | valid |
| P7 (v1) | "the client's own retry policy" | **changed file** | docstring neutralised |
| P8 | none (no rounding direction documented) | — | valid |
| P9 (v1) | "a missing key is a configuration error" | **changed file** | invalid → redesigned |
| P10 | none ("may fetch" is unchanged in B) | — | valid |
| P11 (v1) | "an empty list yields 0.0" | **changed file** | invalid → redesigned |

## 2. The four redesigns (Dev: P2, P3; held-out: P9, P11)

Held-out had not been run, so revising it here is a pre-registration, not a
post-hoc label change. Every revision removes the self-contradiction; none of them
changes what the model sees (the diff stays identical inside each pair).

**P2** — `tax_for`'s docstring was unit-specific ("expressed in dollars") while
variant B's money module works in cents. New docstring: *"using this module's
money unit"*. The unit is now defined only by `money.py`, so A's 100× error is an
external-context defect and B has no internal contradiction. Mechanism M2 kept.

**P3** — returning `None` from a `-> list[dict]` function is a contract break in
both variants. Replaced the whole pair: the diff now removes a defensive copy
(`result = list(items)` → `result = items`), which violates nothing the changed
file documents. A's caller reads the original list after the call (observable
wrong output); B snapshots the length first, so the mutation is invisible.
Mechanism M3.

**P9** — `rate_for`'s docstring declared a missing key to be a configuration
error, so `.get(..., 0.0)` contradicts it everywhere. The docstring is now
neutral ("Return the configured rate") and the contract lives in the A-side
`config.py`: an unset rate must stay absent so callers fail loudly. B always
supplies the key. Mechanism M6.

**P11** — `average`'s docstring promised `0.0` for an empty list. New docstring:
"Return the arithmetic mean"; the empty-series expectation moved to A's
`report.py`, which documents that an empty series reports 0.0. B's `report.py`
rejects an empty series before calling. Mechanism M7.

**P7 (held-out, not a redesign)** — the docstring "the client's own retry policy"
would have been contradicted by passing `retries=1`. Neutralised to "Fetch the
URL." The pair is otherwise unchanged.

## 3. Scorer fixes

1. **`semantic_match` now checks `finding.file_path == pair.diff_file`.** Before,
   a finding in another file could be credited if its line happened to fall in the
   region.
2. **`located` (new `_located` helper) checks file *and* region**, not just the
   line range.
3. **Counterexample tests** (`tests/test_contrast.py`): same line number and
   keywords but a different file; correct file but outside the touched definition;
   only one signature group present.
4. **Renamed in every artefact to "semantic (keyword-assisted)"**, with the
   docstring stating explicitly that it is *not* a full semantic judgement.
5. **Signatures tightened from 1 group to 2 mandatory groups** and the build
   index now rejects any pair with fewer than two groups. Example: P1 needs both
   `strict` **and** one of {keyword, argument, parameter, signature, typeerror,
   unexpected}; P2 needs a unit term **and** a conversion term. Terms were chosen
   from the actual failure mechanism, and `build_index()` enforces the structure.
6. **Human adjudication sheet**: each run now writes `human-review.csv` with the
   automated flags plus empty `human_verdict` / `human_note` columns. Automatic
   scores are labelled as screening; the verdict column is the record of review.

## 4. Evidence retention

Previously `finding_text` was a truncated one-line summary. Now every variant
stores `findings_detail`: the complete structured `ReviewFinding` records
(`file_path`, `start_line`, `end_line`, `category`, `severity`, `summary`,
`explanation`, `evidence`, `suggested_fix`, `source`, `verification_status`).

New results go to a **versioned** directory (`contrast-dev-v2`). The earlier
`contrast-dev/` artefacts are left untouched as the v1 record, together with
`trace-evidence.md`.

## 5. Task parity between V1 and V2

Both prompts now begin with the identical `REVIEW_SCOPE` text; V2 appends only the
tool instructions. A test asserts the shared prefix is byte-identical, so a future
prompt edit cannot silently give the two methods different review objectives.

## 6. Still open

* The keyword screen can still be satisfied by wording that coincides with the
  signature; the human sheet is the guard, and it has not been filled in yet.
* P4, P6, P8, P10 remain neutral because of the caller's input domain (M7/M4/M6).
  That is documented, but it is weaker than a callee that genuinely ignores the
  change (M1/M2).
* Five dev pairs cannot support a statistical claim; held-out (6 pairs) is the
  only set that can, and it has not been run.
