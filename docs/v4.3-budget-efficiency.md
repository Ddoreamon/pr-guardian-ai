# V4.3 — Agent budget efficiency (design only, no implementation)

Status: **proposal**. Nothing in this document is implemented; it fixes the
evaluation rules *before* any optimisation, so a later change can be judged
against a frozen baseline instead of against itself.

Context: real runs repeatedly end `partial` with 4/4 tool calls and 1–2 refusals,
and the trace shows the same file read more than once. Raising `max_tool_calls`
from 4 to 10 is explicitly **not** the plan: it hides the inefficiency and pays for
it in tokens and latency.

## 1. Observations that motivate this

From the V4.1/V4.2 smoke runs (recorded in `docs/v4-evidence-smoke/`):

| Pattern | Example |
|---|---|
| same range read twice | `read_code_context(src/shop/checkout.py, 1-40)` then again after a search |
| read after search of the same file | `search_code("finalise order")` → `read_code_context(src/shop/checkout.py, 1-40)` |
| budget spent before the decisive read | 4 calls used, then `read_code_context(src/shop/orders.py)` denied |
| duplicate detection exists but is passive | `completeness.duplicate_calls` counts repeats; nothing reuses them |

## 2. Research questions

1. **Can a fully identical `read_code_context` be served from cache?**
2. **How does a cache hit keep the real `tool_call_id` and the audit trail?**
3. **How is the tool budget charged for a hit?**
4. **Can the `search_code` → `read_code_context` pair stop re-reading what the
   search already showed?**
5. **When few calls remain, how do we finish judging the evidence we already have?**
6. **How do we measure calls, duplicate rate, partial rate, tokens and finding
   quality?**

## 3. Design sketch (to be validated, not built)

### 3.1 Exact-repeat cache

Key: `(sha, tool, normalised_arguments)`, plus the payload digest that was actually
delivered. Only **exact** repeats are cacheable; a different range is a different
call. The entry stores the delivered payload (post-truncation), so a cache hit can
never reveal more than the original call did.

### 3.2 Audit trail on a hit

A hit is still a real provider tool call: it keeps its own `tool_call_id`, and the
trace records `outcome = "cache_hit"` with `cached_from = <original call_id>`.
Evidence registry semantics stay unchanged — the content was delivered to the model
in this review, so it remains citable, but the registry entry points at the call
that actually delivered it.

### 3.3 Budget accounting

Proposal: a cache hit costs **0** executions but still counts as a *request*, so
`tool_calls_max` limits real work while `review_completeness` keeps showing how much
the model asked for. This keeps `partial` meaningful: a review that only re-reads
cached content should finish, not be truncated.

### 3.4 Search → read de-duplication

Two options, to be tested, not assumed:

* **A. implicit**: if a `search_code` hit already delivered lines N..M of file F,
  a later read of a range inside N..M is served from cache and reported as such;
* **B. advisory**: the tool result of a search carries a hint listing which ranges
  are already in context, leaving the decision to the model.

B preserves model autonomy; A saves calls but hides a decision. The experiment must
compare both against the current baseline.

### 3.5 Finishing under a tight budget

When `remaining_calls == 0` or the round cap is reached, the loop already forces a
final answer. The proposal is to make that explicit: a system message asks the
model to report only findings fully supported by evidence already returned, and the
report marks the run `partial` with `reason = budget_exhausted_before_final_read`.
No extra calls, no silent completion.

### 3.6 Metrics (fixed before the experiment)

| Metric | Definition |
|---|---|
| calls per review | requested / executed / denied (already in the report) |
| duplicate rate | executed duplicates ÷ executed calls |
| cache hit rate | cache hits ÷ requests, only in the cache-enabled arm |
| partial rate | reviews ending `partial` ÷ reviews |
| tokens | provider-reported prompt + completion, per review |
| findings | count, plus source-verified count, per review |
| quality guard | **no change to the frozen held-out sets**; quality is judged on dev cases only, and a regression in verified findings blocks the change |

## 4. Evaluation protocol

1. Freeze a **dev case set** of 6 development PRs (3 cross-file bugs, 3 clean) and
   the queries the model actually issues, captured from a recorded baseline run.
2. Run three arms on the same cases: **baseline (today)**, **cache-only**, and
   **cache + search/read de-dup**.
3. Report the table in §3.6 per arm, plus a per-case diff of tool calls.
4. Acceptance rule: cache-only must not reduce the number of source-verified
   findings, and must reduce executed calls on the repeat-heavy cases. If it does
   not, keep the baseline and stop.

Replays may use a recorded tool-call script instead of the live model, so the
comparison is deterministic and costs nothing; at least one arm must then be
re-checked against a live model run before any claim.

## 5. Non-goals

* No dynamic planner, no self-critique loop, no new retrieval.
* No change to `max_tool_calls` as a "fix".
* No change to the frozen held-out benchmarks, and no re-tuning on them.
* No cache that outlives the review: it is per-snapshot, in-memory, and never
  persisted, so it cannot leak across commits.

## 6. Risks

* A cache hit that is not visible to the model could hide that it is re-reading.
* Zero-cost hits could encourage wasteful search loops; the hit rate must be read
  together with the call count, not instead of it.
* De-duplication across `search_code` and `read_code_context` changes provenance
  wording, and the evidence validator must be re-tested for it.
* Any of this only pays off if repeats are actually common — which §1 suggests but
  a 6-case set cannot prove. Hence the frozen protocol first.
