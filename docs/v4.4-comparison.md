# V4.4 — Evidence-aware planning: A/B result and decision

Branch `feature/v4-evidence-planner` (from `8fbb75f`). Real `deepseek-flash`, six
frozen cases, budgets unchanged at **4 tool calls / 3 rounds**. Nothing in `main`,
Render or any frozen benchmark was touched.

## 1. Is the frozen case set sound?

| Check | Result |
|---|---|
| labels executable | `tests/test_gold.py` fails on all 3 bug branches, passes on all 3 clean branches |
| `main` passes | yes for the 3 bug cases (proving the regression); the 2 clean cases that *add* a function cannot pass on `main`, because the function does not exist yet — the label rests on the head branch |
| gold hidden from the agent | tests live under `tests/`, which is outside the `src/**/*.py` allowlist |
| commit SHAs reproducible | fixed commit dates → identical SHAs on every build |
| required evidence | **derived from the code at freeze time** (gold function span + the cross-file caller span), not hand-written |
| candidate ≠ evidence | coverage counts only `read`/`symbol` registry entries; a `search_code` hit never counts |

The earlier hand-written ranges were wrong (they pointed past the end of a 6-line
file), so they were replaced by derived spans *before* any model run. That is
recorded here rather than silently fixed.

## 3. The planner

`PR_GUARDIAN_EVIDENCE_PLANNER=1` appends six generic planning rules to the system
prompt: list the names the diff depends on and the names that depend on it; answer
the smallest question first; use `find_symbol_definition` when the name is known,
`search_code` when it is not, `read_code_context` only for the lines still needed;
treat a search hit as a candidate; and when one or two calls remain, stop exploring
and answer from the evidence already held.

It contains no case identifiers, no gold paths, and no blanket "read the callee
first" rule. Default is **off**; tool permissions, call budget and round budget are
unchanged.

The planner saved 3 executed calls and 2 refusals, and cut latency from 7.06 s to
6.33 s — but at the cost of **one required evidence range**, and with 5.4% more
prompt tokens (the guidance is extra prompt on every call).

## 5. Failure analysis

* **C3-refactor** is the decisive case: one call was enough to read the changed
  callee, so the planner stopped. It never read the caller in `checkout.py`, so it
  could not show that the rewrite preserves behaviour for the actual call site. The
  answer happened to be right; the evidence was not there. Fewer calls, weaker
  proof — exactly the outcome the acceptance rule forbids.
* **B3-exception** is the case the planner helped: it stopped searching after
  reading both sides (callee + caller) and avoided two refused searches.
* **B1** shows the token cost: the extra guidance did not reduce calls here, it only
  made the prompt longer (5,547 → 8,539 tokens on that case).
* Nothing regressed in correctness or false alarms (6/6, 0 FP), but the baseline was
  already at the ceiling on this six-case set.

## 6. Decision: **No-Go** for promotion

Against the pre-registered criteria:

| Criterion | Result |
|---|---|
| improves required-evidence coverage, or reduces wasted executions | mixed: fewer executions, **lower coverage** |
| does not harm finding correctness | holds (6/6) |
| does not increase false alarms | holds (0) |
| respects safety and provenance | holds (flag does not touch tools) |
| reasonable cost increase | **fails**: +5.4% prompt tokens for fewer calls |

Because coverage dropped, the planner is **not** promoted. It stays behind
`PR_GUARDIAN_EVIDENCE_PLANNER=1` (default off) as an experimental switch, and the
negative result is kept rather than tuned away. "Fewer calls" is not a win on its
own, and this is the evidence for that.

## 7. What would change the verdict

* A larger case set: six cases, three bugs, and a ceiling of 100% baseline accuracy
  cannot separate a planner from noise; the only measurable axis was efficiency.
* A rule that guarantees the caller is read before concluding, instead of the
  generic "stop when few calls remain" — but that is close to encoding the answer,
  which the task forbids.
* Measuring on cases where the baseline actually misses evidence, so a gain is
  possible at all. On these six the baseline already covered 12/12.

## 8. Remaining risks

* One run per arm: run-to-run variance is not measured, so even the call-count
  difference is indicative, not significant.
* The anchored correctness rule (finding on the changed or gold file) is lenient;
  a stricter gold-file rule would score the baseline 1/3. Both are recorded.
* The planner changes only the prompt; a real planner that reorders evidence would
  need a much larger design and a fresh held-out set.
* The six cases are small and synthetic; they exercise cross-file reading, not
  realistic repository noise.
